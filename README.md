# dc-equipment-monitor

Учебная веб-система учёта и мониторинга доступности корпоративного оборудования в ЦОД по дисциплине «Программирование корпоративных индустриальных систем» (ПКИС).

## Статус

Проект находится на этапе планирования. Описанные ниже функции — целевой объём первой версии, а не заявление о готовой реализации. Стек и команды запуска ещё предстоит утвердить. План работ и отметки о выполнении находятся в [TODO.md](TODO.md).

## Назначение

Система объединяет реестр оборудования, сведения о размещении в стойках и результаты автоматических проверок доступности. Сотрудник регистрирует устройство и его TCP-порт; система периодически проверяет соединение, сохраняет результат и отображает историю.

Успешное TCP-соединение подтверждает доступность указанного порта с точки запуска проверки. Оно не гарантирует исправность оборудования или корректность работы приложения за этим портом.

## Функции первой версии

- Создание, просмотр, изменение и удаление записей оборудования и стоек.
- Карточка оборудования: название, уникальный инвентарный номер, тип, адрес, TCP-порт, стойка, признак включённого мониторинга.
- Периодические TCP-проверки с ограничением времени ожидания.
- Последний результат: «Доступно», «Недоступно» или «Не проверялось»; время проверки.
- Отдельное обозначение отключённого мониторинга и устаревших данных.
- История проверок с пагинацией.
- Поиск и фильтрация по стойке, типу и состоянию.
- Обзорная страница со сводными счётчиками.
- Аутентификация и разграничение доступа.

| Роль пользователя | Права |
| --- | --- |
| Администратор | Просмотр, управление реестром и настройками проверок |
| Наблюдатель | Просмотр оборудования, состояний и истории |

Управление в первой версии относится к реестру и настройкам мониторинга. SNMP, агенты, автоматическое обнаружение сети, сбор температуры и загрузки CPU, удалённое питание, изменение конфигурации устройств и внешние уведомления в объём не входят.

## Архитектура

Frontend обращается к Backend через REST API. Backend работает с БД. Модуль мониторинга внутри Backend выполняет периодические TCP-проверки зарегистрированных устройств и записывает результаты в БД. Интерфейс обновляет состояния периодическими запросами к API.

Начальная архитектура: одно серверное приложение, одна БД и один Frontend. Отдельный микросервис мониторинга, очередь сообщений и WebSocket на первом этапе не требуются. При запуске нескольких серверных процессов должен быть определён единственный исполнитель фоновых проверок.

Основные сущности: пользователь, стойка, оборудование, результат проверки. Связи и правила удаления фиксируются до реализации API.

## Запуск и проверка

Исполняемые команды будут добавлены после выбора стека и создания конфигурации. Целевой способ общего локального запуска — Docker Compose; наличие работающей конфигурации пока не заявляется.

До первой сдачи здесь должны появиться: требования к окружению, подготовка настроек, запуск и миграции, загрузка демонстрационных данных, адрес интерфейса и API, создание тестовых пользователей, запуск тестов и остановка приложения. Учётные данные и реальные адреса корпоративного оборудования в репозиторий не публикуются.

## Демонстрация

1. Войти администратором и создать стойку.
2. Зарегистрировать тестовый сервис из локального демонстрационного стенда.
3. Дождаться проверки и показать доступность.
4. Остановить сервис и показать изменение состояния после следующей проверки.
5. Запустить сервис снова и показать восстановление доступности.
6. Открыть историю; под наблюдателем подтвердить отсутствие прав на изменения.

## Правила разработки

- Каждая задача содержит исполнителя, ожидаемый результат и критерии проверки.
- Изменения выполняются в отдельных ветках и объединяются после ревью.
- Изменения API и схемы БД согласуются до реализации.
- Секреты, локальные `.env`, дампы реальных данных и каталоги зависимостей не коммитятся.
- Задача завершена, когда результат проверен, интегрирован и отражён в документации.
