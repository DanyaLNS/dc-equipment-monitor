# ВВЕДЕНИЕ

Объект исследования – веб-система учёта корпоративного оборудования в ЦОД и мониторинга доступности его TCP-портов.

Предмет проектирования – требования, данные, функции, архитектурные взаимодействия и поведение этой системы.

Цель – подготовить полный проектное решение для последующей реализации в рамках практики по предмету \[<mark>ПРЕДМЕТ</mark>\].

## 1.2 Назначение, границы и функциональные требования

Данная разрабатываемая веб-система предназначена для решения следующей проблемы: разрозненный учёт оборудования и ручная проверка сетевого соединения не дают единого актуального представления, о состоянии корпоративного оборудования, тем самым усложняет работу по наблюдению за состоянием оборудования ЦОДа.

Цель разрабатываемой веб-системы заключается в реализации единого реестра учета оборудование и воспроизводимая TCP-проверка зарегистрированного оборудования, а также просмотра результатов двух ролей.

Границы проектируемой веб-системы определяются задачами учёта корпоративного оборудования центра обработки данных (ЦОД), автоматизированного мониторинга доступности его TCP-портов и предоставления полученной информации пользователям.

В функциональные границы системы входят:
•	ведение реестра корпоративного оборудования и стоек ЦОД, включая создание, просмотр, изменение и удаление учётных записей оборудования;
•	регистрация одного или нескольких контролируемых TCP-портов для каждой единицы оборудования;
•	настройка и выполнение периодических проверок доступности зарегистрированных TCP-портов;
•	сохранение результатов проверок, формирование истории мониторинга и определение текущих состояний контролируемых портов;
•	предоставление пользователям сведений об оборудовании, результатах проверок и сводной информации;
•	поиск и фильтрация оборудования по заданным критериям;
•	аутентификация пользователей и разграничение доступа к функциям системы в соответствии с установленными ролями.

Система взаимодействует с корпоративным оборудованием посредством попыток установления TCP-соединений с зарегистрированными адресами и портами. При этом оборудование, сетевая инфраструктура ЦОД и работающие на устройствах службы находятся за пределами программной системы и выступают объектами мониторинга.

В границы проектируемой системы не входят управление физическим оборудованием, удалённое изменение его конфигурации, управление электропитанием, автоматическое обнаружение сетевых устройств, сбор аппаратных показателей (температуры, загрузки процессора и других характеристик), а также мониторинг посредством SNMP и программных агентов.

Результаты TCP-проверок характеризуют исключительно возможность установления сетевого соединения с конкретным портом в момент выполнения проверки. Успешное соединение не является подтверждением аппаратной исправности оборудования или корректности работы предоставляемого им сервиса.

Таким образом, проектируемая система ограничивается задачами инвентарного учёта, проверки сетевой доступности зарегистрированных TCP-портов и информационного представления результатов мониторинга, не затрагивая непосредственное управление инфраструктурой ЦОД. Распределение соответствующих полномочий между пользовательскими ролями приведено в подразделе 1.3. в настоящем тексте проектного документа.  Функциональные возможности проектируемой веб-системы определяются установленными границами предметной области и разграничением полномочий пользователей. Детализация доступных операций и взаимодействий пользователей с системой представлена посредством UML-диаграмм вариантов использования (Use Case) в подразделе 1.4.  в настоящем тексте проектного документа.


## 1.3 Роли и матрица доступа

**ADMIN –** ответственное лицо или сотрудник ЦОДа, занимающийся учетом и актуализацией оборудования в ЦОДе.

**OBSERVER –** ответственное лицо или сотрудник ЦОДа, занимающийся мониторингом состояния и доступностью оборудования.

**GUEST –** не аудецифицированный и не авторизированный пользователь системы.

# 2 Модели данных, функций и архитектуры

## 2.1 Используемые нотации для описания проектных решений

Для графического представления архитектуры, функциональных возможностей, процессов обработки данных и взаимодействия компонентов разрабатываемой веб-системы учёта корпоративного оборудования в ЦОДе и мониторинга доступности его TCP-портов используются следующие нотации моделирования:

IDEF0 (Integration Definition for Function Modeling) – нотация функционального моделирования, предназначенная для описания функций системы, их входных и выходных данных, управляющих воздействий и механизмов выполнения. В рамках проекта применяется для построения иерархической функциональной модели процессов учёта корпоративного оборудования в ЦОД, управления пользовательским доступом, выполнения проверок доступности TCP-портов, предоставления результатов мониторинга и обеспечения эксплуатации системы.

DFD (Data Flow Diagram) – диаграмма потоков данных, предназначенная для описания движения информации между внешними сущностями, процессами и хранилищами данных, а также её преобразования внутри системы. В рамках проекта используется для определения границ веб-системы, отображения основных информационных потоков и детализации процессов регистрации оборудования, обработки результатов проверки TCP-портов, хранения и предоставления данных пользователям.

BPMN (Business Process Model and Notation) – нотация моделирования процессов, предназначенная для графического представления последовательности выполняемых действий, условий переходов, событий и взаимодействий участников процесса. В рамках проекта применяется для описания процедур ведения реестра корпоративного оборудования, выполнения фоновых проверок доступности TCP-портов и просмотра результатов мониторинга с периодическим обновлением информации.

UML Use Case (диаграмма вариантов использования) – диаграмма, предназначенная для описания функциональных возможностей системы с точки зрения её пользователей и других внешних участников. В рамках проекта используется для определения пользовательских ролей, доступных им операций и границ функционального взаимодействия с веб-системой учёта оборудования и мониторинга TCP-портов.

UML Class (диаграмма классов) – диаграмма, предназначенная для описания логической структуры системы посредством представления классов, их атрибутов, операций и взаимосвязей. В рамках проекта применяется для моделирования основных сущностей предметной области, включая корпоративное оборудование ЦОД, контролируемые TCP-порты, результаты проверок доступности, учётные записи пользователей и связанные с ними данные.

C4 Model (модель архитектурного представления C4) – подход к визуализации архитектуры программной системы на нескольких уровнях детализации. В рамках проекта используются три уровня: C1 – для отображения окружения веб-системы, пользователей и внешних взаимодействий; C2 – для представления основных исполняемых частей системы и связей между ними; C3 – для детализации внутренней структуры компонентов серверного приложения, разработанного на языке Go.

Совместное применение указанных нотаций позволяет представить проектные решения на функциональном, информационном, процессном и архитектурном уровнях, обеспечивая согласованное описание структуры веб-системы учёта корпоративного оборудования в ЦОД, механизмов мониторинга доступности его TCP-портов и взаимодействия программных компонентов.

|---------------|---------------------------------------------------|--------------------------------------------------------------------------------------------|
| kind          | LimiterKind \[PK, часть 1; PAIR / IP\]; Служебное | Вид ограничителя: пара «логин/IP» либо отдельный IP-адрес.                                 |
| key_hash      | Hash \[PK, часть 2\]; Служебное                   | Хеш идентификатора окна; исходный IP и пароль не размещаются в диагностических сообщениях. |
| attempts      | List\<Instant\>; Служебное                        | Список моментов попыток за отслеживаемый период; старые записи удаляются.                  |

### 2.3.11 Событие журнала — audit

Серверное событие аудита либо принятое диагностическое событие клиента. Доступ к журналу через отдельную страницу веб-интерфейса не предусмотрен.

Таблица 2.14 – Атрибуты: Событие журнала

| **Поле**      | **Логический тип / обязательность**           | **Смысл и ограничения**                                                                                                                   |
|---------------|-----------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------|
| id            | Identifier \[PK\]; Служебное                  | Неизменяемый идентификатор записи.                                                                                                        |
| occurred_at   | Instant \[UTC\]; Служебное                    | Время приёма события сервером, UTC.                                                                                                       |
| actor_kind    | ActorKind \[USER / OPERATOR / ANONYMOUS\]; Да | Тип субъекта: пользователь, оператор либо анонимный источник.                                                                             |
| actor_user_id | Identifier?; Условно                          | Идентификатор пользователя для событий типа USER; иначе отсутствует.                                                                      |
| actor_os      | Text?; Условно                                | Операционная идентичность для событий типа OPERATOR.                                                                                      |
| actor_role    | Role?; Нет                                    | Роль пользователя на момент события (снимок), если применимо.                                                                             |
| action        | Text; Да                                      | Код действия или события из стабильного серверного перечня.                                                                               |

| outcome       | AuditOutcome \[OK / DENIED / ERROR\]; Да      | Исход операции: успех, отказ или ошибка; не является состоянием TCP-порта.                                                                |
| request_id    | RunIdentifier; Да                             | Идентификатор корреляции запроса для диагностики.                                                                                         |
| details       | Map\<Text,Scalar\>?; Нет                      | Допустимые безопасные детали. Для клиентского события — код, шаблон маршрута, время клиента и ID запроса; без стеков, payload и секретов. |
