# Техническое задание

# Веб-система учёта и мониторинга доступности оборудования ЦОД

**Обозначение:** dc-equipment-monitor.
**Версия документа:** 1.0.
**Версия API:** v1.
**Дата:** 21.11.2026.

## 1. Назначение и область применения

Внутренняя веб-система для сотрудников ЦОД. Администратор ведёт стойки и оборудование, указывает сетевой адрес устройства и один или несколько TCP-портов. Backend периодически пытается подключиться к каждому включённому порту, сохраняет результаты. Пользователи видят доступность портов, историю и сводку.

ADMIN читает и изменяет данные. OBSERVER только читает. GUEST — отсутствие авторизации, отдельной учётной записи с такой ролью нет. Пользователи создаются операционными командами: веб-страница управления пользователями не требуется.

TCP-проверка показывает возможность соединения с конкретным портом, а не аппаратную исправность или правильность работы приложения. SNMP, агенты, аппаратные показатели, автоматическое обнаружение сети, управление питанием и удалённая настройка оборудования не входят в проект.

Контролируемый порт представлен отдельной сущностью `tcp_target`. Устройство может иметь несколько портов. Состояние, расписание и история ведутся для каждого порта отдельно.

## 2. Архитектура и параметры системы

Система состоит из клиентского веб-приложения, серверного приложения на Go и PostgreSQL. Клиент взаимодействует с сервером через REST API. Планировщик мониторинга выполняется внутри серверного приложения. Развёртывание осуществляется через Docker Compose. Конкретный клиентский фреймворк не регламентируется настоящим ТЗ.

Серверное приложение развёртывается в одном экземпляре. Единственный исполнитель мониторинга определяется блокировкой PostgreSQL и номером поколения `epoch`. Пользовательские учётные записи обслуживаются командами администратора на сервере.

| Параметр | Значение по умолчанию | Ограничения |
| --- | --- | --- |
| Интервал проверки порта | 60 с | 10–3600 с, отсчитывается от завершения предыдущей проверки этого порта |
| Общий тайм-аут DNS и TCP | 3000 мс | 100–10000 мс; строго меньше интервала проверки |
| Одновременные проверки | 10 | 1–200 |
| Порог устаревания | 120 с | Не меньше интервала плюс округлённый вверх до секунд тайм-аут; не больше 86400 с |
| Хранение истории | 7 суток | 1–30 суток |
| Обновление активного экрана | 5 с | Без наложения запросов |
| Пул соединений БД | Не более 20 | Включая соединение блокировки монитора |

Непустую стойку удалять запрещено. Удаление оборудования удаляет его порты, результаты и текущие наблюдения. Удаление порта удаляет его результаты и текущее наблюдение. В пределах устройства номер контролируемого порта уникален.

Адрес, порт и переключатели мониторинга изменяют поколение соответствующих целей. Результаты прежнего поколения не становятся текущими. Полные правила отмены проверок и изменения параметров приведены в разделе 3.

## 3. ТЗ для Backend

### 3.1 Состав и результат работы

Один Go Backend в `backend/`: REST API, доступ к PostgreSQL, сессии, планировщик TCP-проверок, очистка данных и техническая диагностика. Для учебного стенда — один процесс и одна БД, зависимости в go.mod/go.sum. Миграции, тесты и команды администрирования — рядом с Backend. Docker Compose запускает Backend, БД, Frontend/прокси и демонстрационный TCP-сервис.

Не создавать REST CRUD для внутренних таблиц session, limiter, runtime, audit, probe_result и current_observation. Клиент не записывает результаты проверок и не назначает служебные версии.

### 3.2 Хранение и бизнес-правила

- Реализовать `users`, `rack`, `equipment`, `tcp_target`, `probe_result`, `current_observation`, `settings`, `runtime`, `session`, `limiter`, `audit` со следующими полями и связями (описание ниже). Логический список attempts в limiter допускается реализовать отдельными временными записями.
- Пользователь: login, уникальный нормализованный login_key (NFC + регистронезависимость), password_hash Argon2id в PHC, role, is_active, auth_version, timestamps. Хеши и токены не выдавать API.
- У оборудования обязательная стойка; адрес общий для всех портов. Уникальны инвентарный номер и номер порта внутри устройства.
- У каждого порта отдельны `version` (редактирование), `monitor_revision` (поколение проверки), `next_due_at`.
- Фоновая запись не изменяет `version` карточки. Изменение названия/типа/стойки не сбрасывает TCP-состояния. Изменение адреса и общего переключателя повышает monitor_revision всех портов устройства и очищает их current_observation; изменение номера порта/его переключателя — только этого порта.
- Повторный PATCH с теми же значениями не сбрасывает наблюдения и не увеличивает версии.
- Историю не переписывать при изменении адреса: сохраняются address_snapshot, port_snapshot, monitor_revision, settings_version и executor_epoch.
- DELETE и проверки выполняются с учётом конкурентного доступа: результат удалённой цели не воссоздаёт запись.
- Изменения и аудит успешного изменения атомарны. История и обновление current_observation записываются одной транзакцией; UNIQUE(run_id) предотвращает повторную запись одной попытки.

### 3.2.1 Состав хранимых данных

Внутренние идентификаторы — положительные целые числа; время хранится в UTC. `created_at` и `updated_at` заполняются сервером. Версии и поколения — положительные целые числа. Поля, помеченные `?`, допускают NULL; остальные обязательны. Внешние ключи применяются, если явно не указано иное.

| Сущность | Поля и ограничения |
| --- | --- |
| users | id PK; login; login_key UNIQUE; password_hash; role ADMIN/OBSERVER; is_active boolean; auth_version; created_at; updated_at |
| rack | id PK; name UNIQUE; location?; description?; version; created_at; updated_at |
| equipment | id PK; rack_id FK rack; name; inventory_number UNIQUE; type SERVER/NETWORK/STORAGE/OTHER; address; monitoring_enabled; version; created_at; updated_at |
| tcp_target | id PK; equipment_id FK equipment; tcp_port; label?; monitoring_enabled; monitor_revision; version; next_due_at?; created_at; updated_at; UNIQUE(equipment_id, tcp_port) |
| probe_result | id PK монотонный; run_id UUID UNIQUE; target_id FK tcp_target; monitor_revision; settings_version; executor_epoch; address_snapshot; port_snapshot; resolved_ip?; status AVAILABLE/UNAVAILABLE; started_at; finished_at; duration_ms ≥0; error_code?; error_text? |
| current_observation | target_id PK/FK tcp_target; monitor_revision; run_id UUID без FK на историю; status AVAILABLE/UNAVAILABLE; checked_at; duration_ms ≥0; resolved_ip?; error_code?; error_text? |
| settings | id=1 PK; interval_seconds; timeout_ms; concurrency; stale_after_seconds; retention_days; version; updated_at |
| runtime | id=1 PK; epoch; owner_instance?; updated_at |
| session | token_hash PK; user_id FK users; issued_auth_version; created_at; last_activity_at; revoked_at? |
| limiter | составной PK(kind, key_hash); kind PAIR/IP; attempts — временные отметки попыток; blocked_until? |
| audit | id PK; occurred_at; actor_kind USER/OPERATOR/ANONYMOUS; actor_user_id?; actor_os?; actor_role?; action; target_type; target_id? без FK; outcome OK/DENIED/ERROR; request_id; details? |

У результата `finished_at >= started_at`; при AVAILABLE поля ошибки равны NULL, при UNAVAILABLE error_code обязателен. settings_version и executor_epoch в истории являются снимками значений, а не внешними ключами. current_observation хранит не более одной записи на порт и не удаляется при очистке истории.

В audit поле actor_user_id обязательно для USER; actor_os — для OPERATOR. Идентификаторы и роль субъекта являются историческими сведениями и не требуют каскадного удаления журнала. details содержит только разрешённые скалярные значения без секретов и полных тел запросов. У действующего сеанса revoked_at равен NULL. Ограничения пользовательских полей заданы в разделе 5.

### 3.3 Алгоритм мониторинга

1. Монитор получает единственную блокировку исполнителя на выделенном соединении PostgreSQL, повышает runtime.epoch. Другие процессы не запускают проверки. Потеря блокировки отменяет проверки; старый epoch не допускается к записи. Блокировка/сверка epoch при публикации исключает гонку со сменой лидера.
2. Выбирает включённые цели с наступившим next_due_at. Включённость равна `equipment.monitoring_enabled AND tcp_target.monitoring_enabled`. Одновременно не более settings.concurrency проверок; одна цель не проверяется параллельно сама с собой.
3. Снимает адрес, порт, monitor_revision, settings.version и epoch; создаёт UUID run_id. Общий тайм-аут охватывает DNS и TCP.
4. Адрес — IPv4, IPv6 либо ASCII DNS без схемы, пути, credentials и порта. Проверяет все разрешённые DNS IP по CIDR allowlist из конфигурации. Если хотя бы один IP запрещён, цель не опрашивается: результат POLICY_DENIED. Для минимальной реализации сортирует разрешённые IP, выбирает первый и подключается непосредственно к нему без повторного DNS. Указывает resolved_ip. Для одной попытки проверяется один разрешённый IP-адрес.
5. Закрывает соединение сразу после успешного установления. Длительность включает DNS. Ошибку отмены/БД/планировщика не превращает в UNAVAILABLE устройства.
6. Перед сохранением повторно проверяет существование, включённость, revision, settings_version и epoch. Несовпадение — результат отменяется и не попадает ни в текущие данные, ни в историю; разрешённая отмена отмечается технически.
7. Сохраняет принятый результат в историю и current_observation, назначает `next_due_at = finished_at + interval_seconds`. Для новых/повторно включённых целей первая проверка назначается сразу с учётом очереди.

При изменении interval_seconds, timeout_ms или concurrency повысить settings.version, отменить старые попытки, сбросить текущие наблюдения и назначить новые проверки. При изменении только stale_after_seconds/retention_days повысить settings.version, сохранить текущие наблюдения, пересчитать их представление; старые выполняющиеся попытки также отменить и переназначить. При рестарте процесса сохранённые наблюдения остаются до обычного устаревания; после восстановления из backup сбрасываются.

### 3.4 Состояние порта

Определяется сервером на момент server_time в таком порядке:

1. Мониторинг устройства или порта выключен → `DISABLED`.
2. Нет наблюдения текущего monitor_revision → `NOT_CHECKED`.
3. `server_time >= checked_at + stale_after_seconds` → `STALE`.
4. Иначе исход наблюдения → `AVAILABLE` либо `UNAVAILABLE`.

`last_result` содержит только наблюдение актуального поколения либо null. STALE не является результатом TCP-попытки. Потеря связи UI с API не является результатом TCP-попытки. Не вводить неоднозначный общий статус устройства: выдавать счётчики состояний его портов.

### 3.5 Доступ и защита

- Пароли — Argon2id; случайный сессионный токен не менее 32 байт, в БД только SHA-256-хеш. Cookie `session`, HttpOnly, Secure при HTTPS, SameSite=Lax, Path=/.
- Сеанс: абсолютный срок 8 часов и 30 минут от последнего разрешённого API-запроса. Поллинг продлевает срок бездействия , но не абсолютный срок.
- Каждый запрос сверяет is_active, auth_version и роль. Команды создания, смены пароля, роли и отключения пользователя реализовать как CLI; изменения повышают auth_version и аннулируют старые сессии.
- Same-origin Frontend/API; изменения требуют проверки Origin и X-CSRF-Token, включая logout и клиентские события. Login требует проверку Origin и JSON, для гостя предсессионный CSRF-токен не нужен.
- После 5 неудачных входов для login/IP за 15 минут блокировка 15 минут; не более 30 попыток/IP за минуту. Ошибки неизвестного логина и неверного пароля одинаковы.
- JSON до 1 МиБ, параметризованные SQL, никакого shell для проверки сети. Ошибки без stack trace, секретов и SQL.

### 3.6 Хранение, кэш, эксплуатация

- История: retention_days (по умолчанию 7). В API сразу исключить записи старше границы; удалять пачками каждые 15 минут, не позднее часа после истечения срока. current_observation не зависит FK от истории.
- Аудит: 30 суток, очистка не позднее следующих 24 часов. Логировать входы, отказы, изменения, безопасные клиентские события. Отдельная веб-страница аудита не нужна.
- Кэш сводки в памяти процесса, не Redis: TTL максимум 2 секунды и не позднее ближайшего stale_at. Инвалидация после записи проверки, CRUD или настройки. Версия кэша/синхронизация должны исключать позднюю публикацию старого вычисления. При ошибке кэша читать БД; при ошибке БД — 503, не возвращать старый кэш как актуальный.
- Индексы: уникальные значения; история `(target_id, finished_at DESC, id DESC)`; выборка по rack_id/type; due-цели. Остальные индексы добавлять по измерениям.
- Технические `/health/live`, `/health/ready`, `/metrics` доступны оператору во внутренней сети/через настройку прокси, не являются пользовательскими страницами. Ready — состояние API, БД и монитора. Метрики: ошибки, очередь, занятые слоты, длительности, cache hit/miss; обновление не реже 60 с. Ресурсы ОС измеряются стендом.
- Backup ежедневно, две копии отдельно от узла; восстановление аннулирует сессии и current_observation, сохраняет историю из копии, переназначает проверки. Документировать и проверить восстановление.

### 3.7 Готовность Backend

Миграции и seed воспроизводимы; API соответствует разделу 5; observer не пишет прямыми запросами; проверены конфликт версий, смена адреса во время проверки, блокировка запрещённой сети, дубли run_id, очистка истории без потери current_observation и отказ БД без ложного UNAVAILABLE. README содержит запуск, CLI пользователей, миграции, backup/restore и тесты.

## 4. ТЗ для Frontend

### 4.1 Экраны и взаимодействия

| Экран | Содержание | API |
| --- | --- | --- |
| Вход | Логин/пароль, общая ошибка, ожидание при 429 | POST /auth/login; GET /auth/me |
| Стойки | Список; ADMIN создаёт, редактирует, удаляет; ошибка непустой стойки | /racks |
| Оборудование | Имя, инвентарный номер, тип, стойка, адрес, переключатель, счётчики состояний портов; поиск/фильтры/страницы | GET /equipment |
| Форма оборудования | Стойка, имя, инвентарный номер, тип, адрес, мониторинг | POST /equipment; GET/PATCH /equipment/{id} |
| Карточка оборудования | Карточка, порты, последние результаты; ADMIN добавляет/редактирует/удаляет порты | GET /equipment/{id}/view; /equipment/{id}/targets; /targets/{id} |
| История порта | Время, адрес/порт на момент проверки, исход, длительность, код ошибки; период/исход/пагинация | GET /targets/{id}/history |
| Сводка | Количество стоек, устройств, портов и распределение портов по состояниям | GET /summary |
| Настройки | ADMIN изменяет interval, timeout, concurrency, stale_after, retention | GET/PATCH /settings |

Экраны портов и истории могут быть вкладками или простыми диалогами в карточке; отдельное сложное приложение для них не нужно. Страница управления пользователями, аудита и кнопка «проверить сейчас» не предусмотрены.

### 4.2 Обязательное поведение

- После login сохранить user и csrf_token только в памяти; cookie хранит браузер. После перезагрузки получать их через /auth/me. Не хранить пароль/сессию/CSRF в localStorage.
- Для всех запросов использовать cookie, для изменений — X-CSRF-Token; отправлять resource version через If-Match для PATCH/DELETE.
- Перед открытием редактирования получать конфигурационную карточку с ETag. При 412 показать конфликт и предложить перечитать данные; не перезаписывать их автоматически.
- ADMIN видит операции изменения; OBSERVER — просмотр. Сервер всё равно проверяет права.
- Активный экран выполняет один обновляющий запрос каждые 5 секунд без наложения. Использовать составной /view для карточки, не опрашивать каждый порт отдельно. Справочники загружать по необходимости, не каждые 5 секунд.
- Скрытая вкладка приостанавливает поллинг, возвращение запускает немедленное обновление. Запрос завершается ошибкой по клиентскому тайм-ауту 5 секунд. При ошибке API показывать баннер и время последнего успешного ответа; старые данные сохранять с пометкой «Нет актуальных данных от сервера».
- На 401 перейти ко входу; 403 — показать отсутствие прав; 409 — объяснить предметный конфликт; 422 — ошибки у полей; 429 — учитывать Retry-After; 503 — показать недоступность системы. Не превращать ошибку API в красные статусы портов.
- Для наступления stale_at между ответами использовать разницу server_time и монотонного времени клиента; свежий AVAILABLE/UNAVAILABLE становится STALE, даже если API перестал отвечать. DISABLED и NOT_CHECKED не превращать в STALE.
- Текстовые статусы: AVAILABLE «Доступно», UNAVAILABLE «Недоступно», NOT_CHECKED «Не проверялось», DISABLED «Мониторинг выключен», STALE «Данные устарели». Результат STALE показывать вместе с последним известным исходом и временем.
- При удалении оборудования предупредить, что удалятся порты и история. При 409 непустой стойки предложить сначала перенести/удалить оборудование.
- Формы защищены от повторной отправки; ожидание, пустые данные и ошибки предусмотрены. Текст выводится безопасно, без интерпретации пользовательского HTML.
- Русский интерфейс, строки вынесены отдельно. Время API — UTC, отображение местное с обозначением часового пояса. Несекретные фильтры можно сохранять в localStorage.
- Адаптивность: 1280×600, 1366×650, 1920×900; 360×640, 390×844, 412×915, включая альбомную ориентацию. Нет общей горизонтальной прокрутки; таблица может прокручиваться внутри.
- Клавиатура, видимый фокус, labels и текстовые статусы. Поддерживаемые браузеры: Chrome, Firefox, Edge, Яндекс Браузер и Safari. Проверяются текущая и предыдущая стабильные версии на дату приёмки. Версии и операционные системы фиксируются в протоколе испытаний.

### 4.3 Готовность Frontend

Проверены вход/выход, CRUD двух ролей, несколько портов, фильтры, история, 401/409/412/422/503, отсутствие наложения поллинга, устаревание при потере API. Есть компонентные тесты ключевых состояний и один интеграционный сценарий на реальном Backend. Команды запуска/сборки/тестов и lock-файл находятся в frontend/.

## 5. Контракт HTTP API v1

### 5.1 Общие соглашения

- Базовый путь `/api/v1`; все пути ниже относительно него. JSON UTF-8; имена полей snake_case.
- ID — положительные десятичные строки, например `"42"`; UUID — строка UUID; версии — положительные целые числа. Дата — ISO 8601 UTC, например `2026-11-21T12:00:00Z`.
- Необязательные возвращаемые значения представлены null; обязательные поля присутствуют. Поля создания с явно указанным default разрешено пропускать.
- Обычный ответ: `{"data": ..., "meta":{"server_time":"..."}}`. Списки дополнительно возвращают page, page_size, total. DELETE/выход/приём событий — 204 без тела.
- Запросы записи принимают только описанные поля. Неизвестные поля — 422; неправильный JSON — 400. PATCH: только переданные поля, минимум одно; null разрешён только nullable-полям.
- Пагинация: page=1 по умолчанию, page_size=20, диапазон 1–100. Пустая страница — 200 с items:[]; неизвестный ID объекта — 404. Списки реестров сортировать по id ASC. offset-пагинация истории не является зафиксированным снимком при параллельном поступлении записей.
- Пользовательские ответы `Cache-Control: no-store`; внутренний серверный кэш сводки разрешён. Статические ресурсы Frontend кешируются отдельно.
- У каждого ответа заголовок X-Request-ID. Поля password_hash, login_key, token_hash, auth_version, limiter/runtime не выдаются.

### 5.2 Конкурентное изменение

GET конфигурационной карточки `/racks/{id}`, `/equipment/{id}`, `/targets/{id}` и `/settings` возвращает ETag, например `"equipment-42-v3"`. Эти карточки не включают изменяющиеся результаты мониторинга, next_due_at или счётчики; мониторинг читается через /view и списки. ETag — непрозрачная строка, Frontend возвращает её целиком в If-Match.

PATCH и DELETE требуют If-Match соответствующей карточки: отсутствует — 428 PRECONDITION_REQUIRED; устарел — 412 VERSION_CONFLICT; объект уже удалён — 404. POST не требует If-Match. PATCH возвращает полную новую карточку и новый ETag; POST — 201 с карточкой, ETag и Location. Проверка версии и изменение выполняются атомарно. Дочерние порты не меняют ETag конфигурации устройства.

### 5.4 Вход и выход

POST /auth/login:

```json
{"login":"admin","password":"example-password"}
```

Ответ 200 (такой же DTO у /auth/me):

```json
{
  "data": {
    "user":{"id":"1","login":"admin","role":"ADMIN"},
    "csrf_token":"opaque-random-value",
    "session_expires_at":"2026-11-21T20:00:00Z"
  },
  "meta":{"server_time":"2026-11-21T12:00:00Z"}
}
```

login — 1–100 символов после trim; пароль — непустая строка до 1024 UTF-8 байт, не нормализовать/не обрезать. Новый login при существующей сессии отзывает текущую сессию браузера и создаёт новую. Неверные credentials или неактивный пользователь → 401 INVALID_CREDENTIALS; лимит → 429 RATE_LIMITED с Retry-After в секундах. /auth/me не выдаёт новый session token. Logout требует CSRF, отзывает серверную сессию; отсутствие/истечение сессии → 401, Frontend всё равно очищает своё состояние.

### 5.5 Стойки

POST /racks, тело (name обязателен, остальные default null):

```json
{"name":"R-01","location":"Зал 1","description":null}
```

DTO Rack:

```json
{"id":"1","name":"R-01","location":"Зал 1","description":null,"version":1,"created_at":"2026-11-21T12:00:00Z","updated_at":"2026-11-21T12:00:00Z"}
```

PATCH принимает name, location, description. name после trim 1–100 символов, уникален с учётом регистра; location до 200, description до 2000. Дубликат → 409 DUPLICATE_RACK_NAME. Удаление непустой стойки → 409 RACK_NOT_EMPTY.

GET /racks?q=R-01&page=1&page_size=20: q до 200 символов, поиск подстроки без учёта регистра в name/location; элемент списка — Rack плюс equipment_count (целое ≥0).

### 5.6 Оборудование

POST /equipment (все поля обязательны, кроме monitoring_enabled с default true):

```json
{"rack_id":"1","name":"srv-01","inventory_number":"INV-001","type":"SERVER","address":"10.10.0.5","monitoring_enabled":true}
```

DTO Equipment = все поля запроса + `id`, `version`, `created_at`, `updated_at`. GET /equipment/{id} возвращает только этот DTO. PATCH принимает любое непустое подмножество полей создания.

name — 1–200 символов после trim; inventory_number — 1–100 после trim, уникален с учётом регистра; type — SERVER/NETWORK/STORAGE/OTHER; address — IPv4/IPv6/ASCII DNS, максимум 253 символа, без схемы и номера порта; rack_id — существующая стойка. Неправильное поле/неизвестная ссылка rack_id → 422 VALIDATION_ERROR. Дубликат inventory_number → 409 DUPLICATE_INVENTORY_NUMBER. Устройство может временно не иметь портов после создания.

GET /equipment поддерживает:

| Query | Семантика |
| --- | --- |
| q | До 200 символов, поиск подстроки без учёта регистра в name/inventory_number/address |
| rack_id | Точное совпадение |
| type | Одно значение EquipmentType |
| monitoring_enabled | true или false, переключатель самого устройства |
| target_state | Одно состояние: устройство попадает, если хотя бы один его порт имеет такое вычисленное состояние |
| page, page_size | Общие правила пагинации |

Фильтры объединяются AND; неизвестные/неправильные параметры → 422. Валидный, но отсутствующий rack_id фильтра даёт пустой список. Элемент списка = Equipment + rack_name + target_counts. Для устройства без портов все счётчики равны 0, а не «Доступно».

```json
{
  "data":{"items":[{
    "id":"42","rack_id":"1","rack_name":"R-01","name":"srv-01",
    "inventory_number":"INV-001","type":"SERVER","address":"10.10.0.5",
    "monitoring_enabled":true,"version":1,
    "created_at":"2026-11-21T12:00:00Z","updated_at":"2026-11-21T12:00:00Z",
    "target_counts":{"total":2,"available":1,"unavailable":1,"not_checked":0,"disabled":0,"stale":0}
  }]},
  "meta":{"server_time":"2026-11-21T12:01:00Z","page":1,"page_size":20,"total":1}
}
```

### 5.7 TCP-порты и составная карточка

POST /equipment/{id}/targets (tcp_port обязателен; label default null; monitoring_enabled default true):

```json
{"tcp_port":443,"label":"HTTPS","monitoring_enabled":true}
```

DTO Target:

```json
{"id":"7","equipment_id":"42","tcp_port":443,"label":"HTTPS","monitoring_enabled":true,"version":1,"created_at":"2026-11-21T12:00:00Z","updated_at":"2026-11-21T12:00:00Z"}
```

PATCH принимает tcp_port, label, monitoring_enabled; перенос к другому оборудованию не поддерживается. tcp_port — целое 1–65535; label — null или до 100 символов. Дубликат внутри устройства → 409 DUPLICATE_TCP_PORT. GET /targets/{id} — Target + ETag, без результатов.

GET /equipment/{id}/view?page=1&page_size=20 возвращает:

```json
{
  "data": {
    "equipment":{
      "id":"42","rack_id":"1","name":"srv-01","inventory_number":"INV-001",
      "type":"SERVER","address":"10.10.0.5","monitoring_enabled":true,"version":1,
      "created_at":"2026-11-21T12:00:00Z","updated_at":"2026-11-21T12:00:00Z"
    },
    "rack":{"id":"1","name":"R-01"},
    "target_counts":{"total":1,"available":1,"unavailable":0,"not_checked":0,"disabled":0,"stale":0},
    "targets":[{
      "id":"7","equipment_id":"42","tcp_port":443,"label":"HTTPS","monitoring_enabled":true,
      "version":1,"created_at":"2026-11-21T12:00:00Z","updated_at":"2026-11-21T12:00:00Z",
      "effective_monitoring_enabled":true,"state":"AVAILABLE","monitor_revision":1,
      "next_due_at":"2026-11-21T12:02:00Z","stale_at":"2026-11-21T12:03:00Z",
      "last_result":{"run_id":"f40a52cc-0857-4dab-aee8-8f101e22c483","status":"AVAILABLE",
        "checked_at":"2026-11-21T12:01:00Z","duration_ms":12,"resolved_ip":"10.10.0.5",
        "error_code":null,"error_text":null}

  "meta":{"server_time":"2026-11-21T12:01:02Z","page":1,"page_size":20,"total":1}

```

Здесь total — количество портов устройства; target_counts считаются по всем его портам, не только странице. Порты сортировать по tcp_port ASC, id ASC. stale_at=null и last_result=null при отсутствии наблюдения; next_due_at=null у отключённых портов. У DISABLED stale_at=null. state и counts вычисляются одним согласованным снимком. Дополнительных вызовов для каждого порта не требуется.

### 5.8 История

GET /targets/{id}/history?from=2026-11-20T00:00:00Z&to=2026-11-21T00:00:00Z&status=UNAVAILABLE&page=1&page_size=20

from/to — необязательные даты UTC: `finished_at >= from`, `finished_at < to`; from должен быть меньше to. status — AVAILABLE либо UNAVAILABLE. Отсутствие фильтров означает всю ещё хранимую историю. Сортировка finished_at DESC, id DESC; старые поколения остаются видимыми. server_time фиксируется на запрос, retention применяется независимо от переданного from.

Ответ data = `{"target_id":"7","items":[ProbeResult]}`; meta содержит server_time, page, page_size, total и retention_cutoff (дата). ProbeResult:

```json
{
  "id":"101","run_id":"f40a52cc-0857-4dab-aee8-8f101e22c483","target_id":"7",
  "monitor_revision":1,"settings_version":1,
  "address_snapshot":"10.10.0.5","port_snapshot":443,"resolved_ip":"10.10.0.5",
  "status":"UNAVAILABLE","started_at":"2026-11-21T12:00:57Z",
  "finished_at":"2026-11-21T12:01:00Z","duration_ms":3000,
  "error_code":"TIMEOUT","error_text":"Время ожидания соединения истекло"
}
```

executor_epoch остаётся внутренним полем. Перечень ProbeError: DNS_ERROR, POLICY_DENIED, TIMEOUT, CONNECTION_REFUSED, NETWORK_UNREACHABLE, CONNECTION_ERROR. AVAILABLE → error_code/error_text null; UNAVAILABLE → error_code обязателен, error_text nullable, до 512 символов. Отмена служебной задачи и ошибка БД не являются ProbeError устройства.

### 5.9 Сводка

GET /summary без query:

```json
{
  "data":{
    "racks_total":10,"equipment_total":50,
    "targets":{"total":100,"available":75,"unavailable":5,"not_checked":5,"disabled":10,"stale":5}
  },
  "meta":{"server_time":"2026-11-21T12:01:02Z","computed_at":"2026-11-21T12:01:01Z"}
}
```

Пять счётчиков состояний взаимоисключающие, сумма равна targets.total. В испытаниях объектом мониторинга считается включённый TCP-порт. Количество устройств может отличаться от количества портов. computed_at относится к вычислению сводки; server_time — время ответа. Обязательны ограничения кэша из раздела 3.6.

### 5.10 Настройки

GET /settings → data:

```json
{"interval_seconds":60,"timeout_ms":3000,"concurrency":10,"stale_after_seconds":120,"retention_days":7,"version":1,"updated_at":"2026-11-21T12:00:00Z"}
```

PATCH /settings принимает непустое подмножество пяти параметров, требует If-Match. Диапазоны: interval_seconds 10–3600; timeout_ms 100–10000 и строго меньше interval_seconds*1000; concurrency 1–200; retention_days 1–30; stale_after_seconds — целое не меньше interval_seconds+ceil(timeout_ms/1000), верхний предел 86400. Проверять итоговое сочетание старых и новых полей, а не только присланные. Нарушение — 422. Семантика отмены/сброса описана в 3.3.

### 5.11 Клиентские события

POST /client-events:

```json
{"events":[{"code":"API_UNAVAILABLE","route_template":"/equipment/:id","occurred_at":"2026-11-21T12:01:00Z","request_id":null}]}
```

events — 1–10; максимум 20 событий/минуту на сессию, лишний пакет целиком → 429. code: API_UNAVAILABLE/UI_ERROR; route_template из `/`, `/equipment`, `/equipment/:id`, `/racks`, `/settings`; request_id nullable — ID связанного серверного запроса, максимум 100 символов. occurred_at — время клиента, сервер отдельно фиксирует время приёма. Произвольный текст, полный URL, тела, стек и секреты запрещены; неподходящее поле → 422. Гость не отправляет события. Ошибку отправки событий не логировать новым клиентским событием.

### 5.12 Единая ошибка

```json
{
  "error":{
    "code":"VALIDATION_ERROR","message":"Проверьте поля формы",
    "fields":{"tcp_port":"Допустимо целое число от 1 до 65535"},
    "request_id":"req-123"
  },
  "meta":{"server_time":"2026-11-21T12:01:00Z"}
}
```

fields всегда объект, пустой при неполевой ошибке. request_id совпадает с X-Request-ID. Frontend принимает решения по code, текст предназначен человеку.

| HTTP | code | Когда |
| --- | --- | --- |
| 400 | INVALID_JSON | Невалидный JSON |
| 401 | UNAUTHENTICATED / INVALID_CREDENTIALS | Нет действующего сеанса / отказ входа |
| 403 | FORBIDDEN / CSRF_FAILED | Нет роли / неверный Origin или CSRF |
| 404 | NOT_FOUND | Не найден ресурс маршрута |
| 409 | DUPLICATE_RACK_NAME / DUPLICATE_INVENTORY_NUMBER / DUPLICATE_TCP_PORT / RACK_NOT_EMPTY | Предметный конфликт |
| 412 | VERSION_CONFLICT | If-Match устарел |
| 413 | PAYLOAD_TOO_LARGE | Более 1 МиБ |
| 415 | UNSUPPORTED_MEDIA_TYPE | Запись с телом не в application/json |
| 422 | VALIDATION_ERROR | Поля или query не прошли проверку |
| 428 | PRECONDITION_REQUIRED | Нет If-Match |
| 429 | RATE_LIMITED | Превышен лимит, есть Retry-After |
| 500 | INTERNAL_ERROR | Неожиданная ошибка без раскрытия внутренностей |
| 503 | SERVICE_UNAVAILABLE | Не доступна БД/необходимая серверная зависимость |

Проверки доступа выполняются до поиска приватного объекта. Каждый маршрут может возвращать общие ошибки; дополнительные 409 применяются по соответствующим ресурсам.

## 6. Порядок разработки и приёмки

### 6.1 Этапы разработки

1. Реализовать БД, вход, стойки, оборудование и порты в соответствии с разделами 2, 3 и 5.
2. Подключить TCP-проверку и одну карточку с состояниями/историей. Демонстрация — два порта у одного устройства, один доступен, другой недоступен.
3. Завершить CRUD, сводку, фильтры, настройки и обработку ошибок.
4. Проверить ограничения, добавить кэш/индексы по измерениям, подготовить отчёт.

Приёмка проводится после выполнения всех требований настоящего ТЗ. Промежуточная демонстрация отдельного сценария не является приёмкой системы.

### 6.2 Проверяемые сценарии

- ADMIN создаёт стойку, устройство и два порта; OBSERVER читает, но его прямой PATCH получает 403.
- Отключение тестового сервиса меняет только соответствующий порт; второй продолжает отображаться независимо.
- Адрес меняется во время TCP-попытки: прежний результат не становится текущим; старая принятая история сохраняет прежний адрес.
- Выключение мониторинга даёт DISABLED; повторное включение — NOT_CHECKED до новой проверки.
- При остановке монитора данные переходят в STALE; при потере API появляется отдельная ошибка связи.
- Удаление непустой стойки запрещено; старый If-Match даёт 412; дубликаты — 409.
- Очистка истории не удаляет current_observation; восстановление backup отзывает сессии и сбрасывает наблюдения.
- Поллинг не перекрывается; карточка не создаёт N отдельных запросов по N портам.

### 6.3 Условия и показатели испытаний

Профиль: 10 стоек, 100 включённых TCP-целей, 5 пользователей/сеансов. 5 запросов/с, 80% чтение и 20% запись, включая поллинг; прогрев 5 минут, измерение 60 минут. p95 карточки/входа ≤1 с, списков/истории/сводки/записи ≤2 с; p99 ≤5 с; неожиданные ошибки ≤0,1%. Первый обход 100 целей при concurrency=10 и timeout=3 с ≤45 с (расчётный нижний ориентир 30 с без накладных расходов). 95% результатов видны в UI не позднее 10 с после сохранения, ошибка связи — не позднее 15 с.

Средний CPU ≤70%, RAM максимум ≤80%, свободное место ≥20%, измерения каждые 10 с; пул БД ≤20 соединений, включая соединение блокировки монитора. Запуск ≤60 с, завершение ≤30 с. Установка на подготовленном узле ≤30 минут. Backup: потеря данных ≤24 ч, восстановление ≤2 ч при исправной копии и готовом оборудовании. TLS 1.2/1.3.

Целевой коэффициент доступности — 99% за календарный месяц; плановые остановки учитываются как недоступность. Измерение выполняется авторизованным запросом раз в минуту с тайм-аутом 5 с. Месячный показатель оценивается отдельно от часового нагрузочного испытания. В протоколе указываются период наблюдения, результаты измерений и отклонения от требований.

Клиентский стенд: настольный компьютер с процессором от двух ядер и ОЗУ от 4 ГиБ либо мобильное устройство Android с ОЗУ от 3 ГиБ. Сеть — от 10 Мбит/с, p95 RTT не более 100 мс, потери не более 0,1%. Основные ОС испытаний — Windows 10/11 и Ubuntu 24.04; Safari проверяется на macOS. Конфигурация серверного стенда, версии ОС, БД, браузеров и зависимостей фиксируются в протоколе. Ресурсные показатели оцениваются на указанном стенде.
